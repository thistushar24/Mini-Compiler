\# Mini Compiler IR Specification



\## 1. Purpose



The Intermediate Representation (IR) is the interface between the frontend and optimization/backend stages.



Pipeline:



Source

→ Lexer

→ Parser

→ AST

→ IR

→ Optimization

→ Code Generation

→ Target Code



Person 3 owns the IR generation and code-generation stages.



Person 4 operates on the IR produced by `IRGenerator`.



\---



\## 2. IR Structure



The compiler uses a three-address-code style representation.



A typical instruction has the form:



&#x20;   result = operand1 OP operand2



Example:



&#x20;   t1 = x + y



The IR is represented by `IRProgram`, which contains an ordered list of `IRInstruction` objects.



\---



\## 3. Operand Types



An IR operand can be one of three types:



\### CONSTANT



Represents a literal value.



Examples:



&#x20;   10

&#x20;   20

&#x20;   3.14



\### VARIABLE



Represents a source-level variable.



Examples:



&#x20;   x

&#x20;   y

&#x20;   count



\### TEMPORARY



Represents a compiler-generated temporary value.



Examples:



&#x20;   t1

&#x20;   t2

&#x20;   t3



Temporary names are generated by `IRGenerator`.



\---



\## 4. Supported IR Operations



\### Data movement



&#x20;   MOV



Example:



&#x20;   x = 10



IR:



&#x20;   MOV x, 10



\---



\### Arithmetic



&#x20;   ADD

&#x20;   SUB

&#x20;   MUL

&#x20;   DIV

&#x20;   MOD



Examples:



&#x20;   t1 = x + y

&#x20;   t2 = x - y

&#x20;   t3 = x \* y

&#x20;   t4 = x / y

&#x20;   t5 = x % y



\---



\### Comparison



&#x20;   CMP\_EQ

&#x20;   CMP\_NE

&#x20;   CMP\_LT

&#x20;   CMP\_GT

&#x20;   CMP\_LE

&#x20;   CMP\_GE



Examples:



&#x20;   t1 = x > y

&#x20;   t2 = x == y



Comparison instructions produce a value that can be used as a branch condition.



\---



\### Unary operation



&#x20;   NEG



Example:



&#x20;   t1 = -x



\---



\### Control flow



&#x20;   LABEL

&#x20;   JUMP

&#x20;   BRANCH



Example:



&#x20;   BRANCH t1, L1, L2



means:



&#x20;   if t1:

&#x20;       goto L1

&#x20;   else:

&#x20;       goto L2



Example:



&#x20;   JUMP L3



means:



&#x20;   goto L3



Example:



&#x20;   L1:



defines a control-flow label.



\---



\## 5. IR Examples



Source:



&#x20;   let x = 10;

&#x20;   let y = 20;

&#x20;   x = x + y;



IR:



&#x20;   MOV x, 10

&#x20;   MOV y, 20

&#x20;   ADD t1, x, y

&#x20;   MOV x, t1



\---



Source:



&#x20;   if (x > 20) {

&#x20;       x = x - 1;

&#x20;   }



IR:



&#x20;   CMP\_GT t1, x, 20

&#x20;   BRANCH t1, L1, L2



&#x20;   L1:

&#x20;   SUB t2, x, 1

&#x20;   MOV x, t2

&#x20;   JUMP L3



&#x20;   L2:

&#x20;   JUMP L3



&#x20;   L3:



\---



\## 6. Optimization Contract



Person 4 must operate on `IRProgram` / `IRInstruction`.



The optimizer must NOT parse source code.



The optimizer must NOT directly modify the AST.



The optimizer should preserve program semantics.



Conceptually:



&#x20;   IRProgram input

&#x20;         ↓

&#x20;      Optimizer

&#x20;         ↓

&#x20;   IRProgram output



The optimized IR must remain valid according to this specification.



\---



\## 7. Allowed Optimizations



The optimizer may implement:



\### Constant folding



Before:



&#x20;   ADD t1, 10, 20



After:



&#x20;   MOV t1, 30



\### Constant propagation



Before:



&#x20;   MOV x, 10

&#x20;   ADD t1, x, 5



After:



&#x20;   MOV x, 10

&#x20;   ADD t1, 10, 5



Further constant folding may reduce this to:



&#x20;   MOV t1, 15



\### Algebraic simplification



Examples:



&#x20;   ADD t1, x, 0



may become:



&#x20;   MOV t1, x



&#x20;   MUL t1, x, 1



may become:



&#x20;   MOV t1, x



\### Dead-code elimination



Instructions whose results are never used may be removed when doing so is safe.



\### Common subexpression elimination



Repeated equivalent expressions may reuse an existing temporary when their operands have not changed.



\---



\## 8. Control-Flow Requirements



Optimizations must preserve:



\- LABEL instructions required by control flow.

\- JUMP targets.

\- BRANCH targets.

\- Correct true/false branch destinations.

\- Program execution semantics.



An optimization must not remove a label if another instruction still references it.



\---



\## 9. Backend Contract



The code generator accepts valid IR:



&#x20;   CodeGenerator::generate(const IRProgram\& program)



Therefore the backend does not need to know whether the IR was optimized.



Both of these are valid:



&#x20;   IRGenerator

&#x20;       ↓

&#x20;   CodeGenerator



and:



&#x20;   IRGenerator

&#x20;       ↓

&#x20;   Optimizer

&#x20;       ↓

&#x20;   CodeGenerator



\---



\## 10. Ownership



| Component | Owner |

|---|---|

| Lexer | Person 1 |

| Parser | Person 2 |

| AST | Person 2 |

| Semantic Analysis | Person 2 |

| IR Design | Person 3 |

| AST → IR | Person 3 |

| CFG | Person 3 |

| Optimization | Person 4 |

| IR → Target Code | Person 3 |



Person 4 should not change the IR instruction format without coordinating with Person 3.



\---



\## 11. Important Implementation Rule



The optimizer should work with structured IR objects.



Do not perform optimization by searching and replacing strings in printed IR.



Correct:



&#x20;   IRInstruction

&#x20;   IRProgram

&#x20;   IROperand



Incorrect:



&#x20;   string manipulation of IRProgram::toString()



The textual representation is intended for debugging and testing.
